# DESIGN

## agentcore and why it is shaped this way

`agentcore/` is a small runtime with no hospital code (a test checks its imports). A **tool registry** turns Python functions with Pydantic inputs into Claude tools, rejects unknown fields and bad input before the tool runs, and turns every failure into a result the model can read. The **loop** (`client.messages.create`, no framework, no tool runner) has a step limit, a whole-run time limit, a status for every stop reason (a truncated or refused reply is never treated as an answer) and one shared `execute_tool_call` path. **`call_model`** gives each attempt a timeout, retries rate limits, 5xx and connection errors with capped backoff and turns the SDK's own retries off so they cannot multiply ours. **Hooks** run before and after every model and tool call and can allow, block with a reason, or *confirm*, which parks the call so the app can run it later through the same path. A hook that crashes blocks the call. **Traces** record every attempt with inputs, outputs, time, tokens and cost, and spans are scrubbed (API keys, a redact hook for phone numbers). The **session store** is an interface (in-memory now) with per-session locks and first-owner-wins binding.

## What the model decides, what code decides

The model understands the patient, picks tools and arguments, and writes friendly text. Code decides everything that can hurt someone: who the patient is (the `/chat` phone only; no tool accepts a phone), whether a write may run (own data, current state, hospital clock, 4-hour rule), whether the patient clearly confirmed the exact action, what the read-back says (built from the tool arguments), what is reported after a write (built from the verified result), and whether a message is an emergency (code phrases first). Confirmation needs two independent checks: a whole-word code check (explicit yes, no negation, question or extra request; English, Hindi, Hinglish) and a small model verdict. A pending action lives for exactly one patient message.

## Failure handling

- **Hospital errors**: classified as definite (4xx), not sent, or unknown (timeout after send, any 5xx: a 503 can follow a saved write). Reads retry; writes never retry in the client.
- **Booking**: one idempotency key per confirmed operation (new for every new operation), same-key retries, then a lookup for evidence.
- **Reschedule and cancel** (no key): a request that never left is retried once; after a 5xx reply the hospital state is checked twice and the write retried once only if the target state is still not visible (a reply means the hospital finished handling it); after a timeout, a 202 or any non-5xx reply the request may still be running, so it is never retried and stays *unknown* if the state shows nothing. A matching read proves the state, not who caused it. A 2xx reply is believed only if it names the target we asked for; 202, redirects, 408, 429 and other 4xx count as unknown.
- **Unknown across turns**: the session keeps unresolved writes. A repeated booking reuses the same idempotency key; a booking for the same patient, doctor and day at another time, and any other change to the same appointment or bill, is blocked and flagged; unrelated bookings go ahead. A booking is proved only by a same-key 2xx reply: a matching record seen by lookup is current state, not proof that this request made it (records carry no idempotency key), so it stays unknown. A booking elsewhere (another doctor or day) is allowed while one is unresolved, but its read-back says both may exist; we do not assume it replaces the first. The state lives in the in-memory store, so a restart forgets it (a durable store is missing).
- **Reads and read-backs fail safe**: a write is not proposed unless the doctor can be named; a reply with a record that may be ours but is unreadable (or whose owner is unclear) fails the whole read instead of looking like "no records"; other patients' records are dropped. A booking is a plain failure only if every attempt never left; one unknown attempt keeps it unknown.
- **Diagnostics**: every hospital error on a confirmed write adds a `hospital` span to the trace with only our own classification: operation name, category (`definite`, `not_sent`, `unknown`, `handler_exception`), HTTP status when there was a reply, and the error code if it has the documented shape. No hospital text, patient content or credentials; an `unknown` span says `saved: unknown`, because a status never shows whether a write was saved (a 503 comes before or after the save). `GET /trace/{session_id}` returns that session's traces only (`session_id`, `traces`, `total_cost_usd`, `cost_complete`); a trace still holds the patient's messages, the model prompts and tool inputs and outputs, with phone numbers masked and API keys scrubbed. That is not a privacy guarantee. Set `TRACE_TOKEN` and add real authentication before real patients. A handoff is a flag in the response (human request, distress through the router, repeated failure, emergency, the four-hour rule, an unknown write outcome). Nothing is sent to staff and nothing is acknowledged; the replies say the chat is flagged and give the front desk number. There is no handoff inbox.
- **In flight**: before a confirmed write is sent, the session is saved with an in-flight marker and without the pending yes, so a crash mid-write leaves a restarted chat unable to repeat it; the marker blocks other changes to that target (a repeated booking reuses its key). It is only as durable as the store: the in-memory store forgets it on restart, so a real restart still loses it until a durable store is added. What can be reconciled under this API: a booking by its idempotency key; everything else only by current state, which proves the state and not which request caused it.
- **Approval** covers the exact call and the details read back; if the record changes before the yes, the patient is asked again. Hospital replies are untrusted: other phones' records are dropped, the hospital's error text is never passed on, and free text (doctor names, bill descriptions) is cut to one plain line and kept out of read-backs. That removes markup, not meaning: a sentence in ordinary language inside a doctor name or bill description still reaches the model in tool results. What stops harm is code (own-data checks, the patient's yes on code-built details, the 4-hour rule), not filtering; the model's wording and which valid action it proposes can still be steered.
- **Payment link**: never retried after an unknown result (duplicates cannot be ruled out and there is no way to list links).
- Finding nothing is never proof of failure: the outcome stays *unknown*, the chat is flagged, and the reply says it could not be confirmed. Only 2xx or the target state counts as success; only a definite error counts as failure.
- **Model outage**: two failed turns in a row flag a handoff. **Emergency check failure**: conservative reply, no writes.
- A **handoff is only a flag** in the response. Nothing pages staff, so replies say the chat is flagged and give the front desk number; they promise no contact.
- Three filters catch obvious mistakes: numbers in info replies must come from `hospital_info.md`; insurance, cashless and similar topics the file never mentions are replaced with "I don't have that information"; no dosages or "it's probably nothing". They are nets, not guarantees: a paraphrase ("we work with your provider"), another language, another uncovered topic or advice in other words passes, and a hedged reply that names a listed topic is replaced too. Prompts and evals cover the rest.
- **Time limits**: `not_before` / `not_after` are inclusive HH:MM. The write policy reads the patient's latest message for a limit ("after 5 pm" means from 17:01, "at or after 5 pm" 17:00, "not after 6 pm" up to 18:00, English words and Hinglish "baje ke baad") and refuses a call whose limit differs or is missing; a time without AM or PM is a question for the patient, not a guess. It also refuses a proposal outside its own limit. A limit with no new phrase in the latest message is kept as the model carried it; a changed preference must replace it. Hindi script, other languages and other wording are not read, so a limit can still be missed. An alternative after a lost race keeps the limit and still gets its own read-back and yes.

## Models, cost and speed

Router, emergency, confirmation checks and all four agents use `claude-haiku-5-5` with thinking turned off. Measured from traces: a calm run of 13 scenarios was 125 model calls for $0.0195; each of three chaos runs was about 130 calls for about $0.021; a model call took about 0.8 to 1.0 s. I did not run Sonnet, so there is no measured comparison; by price alone it would be about 20 times more per token. I kept Haiku because the failures in `EVALS.md` are not ones I expect a bigger model to fix by itself (they are about confirmation flow and wrong tool arguments), but that is an untested guess.

## Evals

Three chaos runs: 10/13, 10/13, 12/13 (see `EVALS.md`). Scenario 03 fails in all three: after a lost race the next slot is offered with a read-back, but the patient's "yes, book that one" is not accepted; cause not yet confirmed. Others: a wrong doctor id in a tool call, a lost race with no turn left to confirm, an unknown payment-link result (by design not retried), a name the model re-asked for, and a phrase-match artifact in scenario 09.

## Phone calls instead of chat

Confirmation would need spoken read-backs and a spoken yes, so the whole-word text check would be replaced by speech transcripts with confidence and a re-ask on low confidence. Latency matters far more (about 3 model calls per turn is too slow: merge the emergency and routing checks, stream replies, cache the prompt). The emergency check must work on partial transcripts and interrupts. Caller identity from caller ID is weaker than a verified WhatsApp number, so writes would need a second factor.

## Missing before real patients

Real staff paging and a handoff queue (today only a flag); authentication on `/trace` (it stays open because the assignment defines it with only a session id; setting `TRACE_TOKEN` requires a bearer token, and it is unset by default, so anyone with a session id can read the messages, with only phones masked); model pauses (`before_model` Confirm returns `paused`, and the app must resume with `messages + result.messages` and track the remaining steps and time itself; `after_model` Confirm blocks and cannot resume, and the chat flow does not use the pause yet; none of this is tested with live Claude); a durable session store with expiry; rate limiting and abuse controls; Marathi and wider emergency-phrase coverage with measured recall; a real evaluation set with many runs per scenario; monitoring and alerting on unknown write outcomes; concurrency tests with real load (writes from two chats of one patient can interleave: the hospital, not this code, arbitrates); a security review of prompt-injection paths through stored patient names and tool text; and review of the cost caps.
