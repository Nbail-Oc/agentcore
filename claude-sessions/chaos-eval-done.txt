  3. Current weaknesses (naive agent)

  1. Cross-patient access and writes. cancel(appointment_id)

  3. No 4-hour rule. Nothing reads /now. Scenario 06 fails by design.
  4. No emergency check. Nothing runs before the model (app.py:22 TODO).
     Scenario 08 has no path to pass.
  5. handoff and emergency are never set. ChatResponse defaults them to False
     (schemas.py:20-21). Scenarios 06 and 08 check these fields.
  6. Crash leaves a broken session. run_tool is unguarded. Bad args (**args
     mismatch) or an HTTPStatusError from raise_for_status raises out of handle.
     The assistant tool_use was already appended (naive_agent.py:102) with no
     matching tool_result. The next turn in that session will likely fail with a
     400 from the API. The HTTP error case is by reading only; I did not
     reproduce either.
  7. Duplicate-booking risk on 503 commit-then-fail. book() never sends
     idempotency_key (hospital_client.py:24). A retry after a saved-but-503
     booking creates a second appointment. Nothing checks the real state before
     answering ("never say something happened when it didn't").
  8. No step limit. while True (naive_agent.py:98). A tool-use loop can run
     unbounded and bill unbounded.
  9. No max_tokens, refusal, or other stop-reason handling. Reply is whatever
     text is in the last response (naive_agent.py:112).
  10. Blocking calls in async code. handle is async but calls sync anthropic and
      sync httpx. Under chaos latency (0.3-2 s per call), one slow call blocks
      all sessions.
  11. Global unbounded HISTORY (naive_agent.py:81). No lock per session, no
      persistence, no trimming. Concurrent requests on one session can
      interleave.

      plain reply and one tool round-trip.
  13. Wrong model for router. MODEL = "claude-sonnet-5-5" (naive_agent.py:15).

     │ 3. Critical design decisions                                            │
     │                                                                         │
     │ 3.1 Confirmation and pending actions [REQ read-back + clear yes;        │
     │ mechanics REC]                                                          │
     │                                                                         │
     │ Plain language: when the model wants to write, code parks the call and  │
     │ builds the read-back from the parked args (doctor, day, date, time, or  │
     │ bill and amount). The model writes friendly prose in the patient's      │
     │ language; code appends the details block so the patient confirms        │
     │ exactly what will run. Pending = {id (random), tool, args, args_hash,   │
     │ details_text, agent, phone, created_turn}.                              │
     │                                                                         │
     │ Authorization rule (all must hold): (1) a pending action exists for     │
     │ this phone+session and was created in the previous turn; (2) the Haiku  │
     │ judge, shown the stored read-back and the patient's message, returns    │
     │ confirm; (3) a code check agrees: message is short (about 20 words or   │
     │ fewer), contains an affirmative token from a small EN/HI/Hinglish list  │
     │ (yes, ok, okay, sure, confirm, go ahead, haan, ji, theek hai, kar do,   │
     │ book it, हाँ, ठीक है ...) and no blocker token (no, not, don't, but,      │
     │ instead, wait, change, nahi, mat, lekin ...). Any disagreement means    │
     │ not confirmed (fail closed; patient is re-asked). "Okay book whatever"  │
     │ passes (specific read-back plus affirmative).                           │
     │                                                                         │
     │ ┌───────────────────────────┬────────────────────────────────────┐      │
     │ │       Patient reply       │               Result               │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │                           │ consume pending before executing   │      │
     │ │ clear yes                 │ (so a retry/double "yes" can't run │      │
     │ │                           │  twice); execute stored call       │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ yes but qualified ("yes   │ not confirmed; treated as a        │      │
     │ │ but 6pm", "yes and also   │ change; old pending cleared; agent │      │
     │ │ cancel...")               │  proposes new read-back            │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │                           │ old cleared; agent re-proposes;    │      │
     │ │ changed details           │ new pending replaces (max one      │      │
     │ │                           │ pending)                           │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ question                  │ cleared (fail closed); answer,     │      │
     │ │                           │ then agent re-offers a read-back   │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ rejection                 │ cleared; no write                  │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ topic change              │ cleared; router picks the agent    │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ asks for a person         │ cleared; handoff, handoff=true     │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │                           │ cleared before anything else; no   │      │
     │ │ emergency                 │ execution even if the message says │      │
     │ │                           │  "yes"                             │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ unclear/maybe             │ cleared; clarifying question       │      │
     │ └───────────────────────────┴────────────────────────────────────┘      │
     │                                                                         │
     │ Retention rule: a pending action lives across exactly one patient       │
     │ message boundary; every outcome clears it. [LIMIT] A patient who asks a │
     │ side question must re-confirm; accepted for safety and simplicity.      │
     │                                                                         │
     │ 3.2 Safety at execution time [REQ own-data, 4-hour rule; mechanics REC] │
     │                                                                         │
     │ The confirmed action is run by agentcore.execute_tool_call(registry,    │
     │ name, args, ctx), the same function run_agent uses for model-requested  │
     │ calls: Pydantic validation, before-tool hooks, execution, after-tool    │
     │ hooks, trace span, error-to-result. ctx.approved (fingerprints of       │
     │ confirmed calls) is set only by app code from the patient's own         │
     │ message, never by model or tool output. Hook order for every write:     │
     │ ownership (fresh list for ctx.phone; not found returns the same generic │
     │ "not found" as a missing id) -> state (appointment exists and is        │
     │ booked; bill unpaid; slot in the future per hospital /now) -> 4-hour    │
     │ (fresh /now; strictly less than 4h blocks, exactly 4h allowed; sets     │
     │ handoff) -> confirm gate (allow only if fingerprint is approved,        │
     │ otherwise park). Anything that changed since read-back blocks the write │
     │ and the model explains.                                                 │
     │                                                                         │
     │ 3.3 Write recovery [REQ never claim, never double-book; strategies REC, │
     │ from mock API]                                                          │
     │                                                                         │
     │ Outcomes: success (2xx, or verified state), definite failure (409       │
     │ slot_taken, 400/404 with code, or verified not-applied), unknown        │
     │ (timeout, connection reset after send, 503 on a write, malformed body). │
     │                                                                         │
     │ Write: Reads                                                            │
     │ Strategy: Retry with backoff (up to 3).                                 │
     │ ────────────────────────────────────────                                │
     │ Write: Book                                                             │
     │ Strategy: idempotency_key = per-operation id (the pending action's      │
     │   random id): stable across retries of that one operation, new for      │
     │   every new operation (a content hash would wrongly return an old       │
     │   cancelled booking for a re-booking). On unknown: retry same key       │
     │   (up to 2 more); still unknown: list the phone's appointments and      │
     │   match doctor+start; found = success, list ok and no match = not       │
     │   booked, list fails = unknown. slot_taken = definite failure           │
     │   (offer other slots, new read-back needed).                            │
     │ ────────────────────────────────────────                                │
     │ Write: Reschedule                                                       │
     │ Strategy: No key, so never blind-retry. On unknown: fetch the           │
     │   appointment fresh. start == new_start = success; start ==             │
     │   old_start = not applied, retry once (may now be slot_taken =          │
     │   definite failure); unclear = unknown.                                 │
     │ ────────────────────────────────────────                                │
     │ Write: Cancel                                                           │
     │ Strategy: Same as reschedule: verify status. cancelled = success;       │
     │   booked = retry once; not_active is verified, not trusted.             │
     │ ────────────────────────────────────────                                │
     │ Write: Payment link                                                     │
     │ Strategy: No automatic retry after an unknown outcome (cannot           │
     │   verify, duplicates possible). Retry only when the request             │
     │   provably never left (connection refused before send). Unknown:        │
     │   tell the patient honestly, offer "try again (may create a second      │
     │   link)" as a new confirmed action with a new id, or handoff.           │
     │                                                                         │
     │ Tools return structured {outcome: success|failed|unknown, ...}; code    │
     │ appends an authoritative outcome block ("Booked: Dr. X, Fri 4 Dec       │
     │ 17:30, ref A1007" / "Not confirmed; staff will check"). Unknown also    │
     │ flags handoff. [LIMIT] The model's free-text prose could still          │
     │ contradict the block in some language; mitigated by the truth           │
     │ instruction in tool results, the block, and evals. Cost note [ASSUME]:  │
     │ the no-retry payment-link rule may fail scenario 10 in about the share  │
     │ of chaos runs where that call 503s; reported honestly.                  │
     │                                                                         │
     │ 3.4 Emergency handling [REQ before router, EN/HI/Hinglish; mechanics    │
     │ REC]                                                                    │
     │                                                                         │
     │ Order on every message: (a) normalized keyword/phrase layer (English,   │
     │ Devanagari Hindi, Hinglish) -> immediate emergency, no model call; (b)  │
     │ Haiku JSON classifier via call_model (short timeout, 1 retry, strict    │
     │ Pydantic parse). Classifier failure (timeout, API error, invalid JSON): │
     │ fail safe. If a soft symptom word is present (pain, dard, seene,        │
     │ saans, khoon, bleeding, behosh, chakkar, ...), treat as emergency;      │
     │ otherwise continue read-only for this turn (confirm gate refuses        │
     │ writes) with a "if this is an emergency call 108" line. Emergency reply │
     │ is a fixed bilingual template (English plus Hindi): 108 or nearest ER   │
     │ (ours is open 24h), no medical advice. Flags: emergency=true,           │
     │ handoff=true (staff flag; there is no real paging system in scope),     │
     │ agent=safety. Pending is cleared.                                       │
     │                                                                         │
     │ Tests (offline, no key): table of EN / Devanagari / Hinglish phrases    │
     │ including scenario 08's text; classifier                                │
     │ true/false/invalid-JSON/exception/timeout via FakeClaude; emergency     │
     │ while a confirmation is pending (message says "yes", nothing written,   │
     │ pending cleared). [LIMIT] Recall is only measured on tested phrases;    │
     │ Marathi and indirect phrasing ("he isn't responding") rely on the       │
     │ classifier; false alarms are accepted, misses are not; we never claim   │
     │ 100%.                                                                   │
     │                                                                         │
     │ 3.5 Identity and trace isolation [REQ own-data; mechanics REC]          │
     │                                                                         │
     │ - Verified phone enters only through RunContext built in /chat. No tool │
     │   input schema contains a phone or patient identity; registry           │
     │   validates with unknown fields forbidden, so a model-supplied phone is │
     │   rejected. book forces phone = ctx.phone; patient_name is              │
     │   length/charset limited.                                               │
     │ - Ids are validated by pattern (^A\d+$, ^B\d+$, ^d\d+$), dates and      │
     │   times parsed, path segments URL-quoted, and the hospital client       │
     │   exposes only named functions (no _admin). A test greps agent_service/ │
     │   for _admin.                                                           │
     │ - Sessions: SessionStore.bind(session_id, phone) is first-use-wins; a   │
     │   different phone reusing a session id gets 409 and no data. State      │
     │   therefore maps 1:1 session_id -> phone, and GET /trace/{session_id}   │
     │   can never mix two patients (no collision handling needed).            │
     │ - [LIMIT] /trace/{session_id} is unauthenticated per the spec; anyone   │
     │   with the id can read it. Mitigation without auth infrastructure:      │
     │   phone masked (******3210), no API keys or headers ever stored, error  │
     │   text truncated. DESIGN.md lists trace auth as a production gap.       │
     │                                                                         │
     │ 3.6 Consistent runtime hooks [REQ hooks around model and tool calls]    │
     │                                                                         │
     │ Router, emergency classifier, confirmation judge, human-agent reply and │
     │ specialists all call call_model, so all get timeout, retry/backoff,     │
     │ before/after-model hooks and a trace span (cost per conversation = sum  │
     │ of spans for one trace_id). Real use of model hooks: a per-turn         │
     │ cost/call budget guard. agentcore only knows Allow | Block(reason) |    │
     │ Confirm(details); "Confirm" means "this call needs end-user consent".   │
     │ It never knows what a booking is. The hospital hook decides which tools │
     │ are writes and what details to show, and checks ctx.approved.           │
     │                                                                         │
     │ Parallel tool calls: executed in order; every tool_use gets a           │
     │ tool_result. After the first Confirm, the loop skips all remaining      │
     │ calls in that response with is_error results ("not executed: another    │
     │ action is awaiting confirmation") and ends the turn after the model's   │
     │ next reply. A Block does not skip the others. Two writes proposed at    │
     │ once means only the first is parked.                                    │
     │                                                                         │
     │ 3.7 Context and handoffs [REQ context carries across handoffs]          │
     │                                                                         │
     │ One shared text history per session; every agent sees the whole         │
     │ conversation, so no re-asking. Tool traffic stays inside a turn. This   │
     │ is sufficient because the code-appended details/outcome blocks (ids,    │
     │ doctor, date, time, bill, amount) are part of the stored assistant      │
     │ text, and agents can re-fetch live data with read tools. Structured,    │
     │ not in prose: pending (bound to phone and session, never trusted from   │
     │ text), active_agent. History capped at 30 messages. [LIMIT] An old fact │
     │ beyond the cap is forgotten; typical chats are far shorter.             │
     │                                                                         │
     │ 3.8 Information safety [REQ facts only from hospital_info.md, no        │
     │ medical advice]                                                         │
     │                                                                         │
     │ - Info agent has no tools and receives the whole hospital_info.md in a  │
     │   delimited block; rules: answer only from it, otherwise say you don't  │
     │   know and offer staff.                                                 │
     │ - Number-grounding guard (after-model hook, deterministic): every       │
     │   currency amount, clock time and phone number in an info reply must    │
     │   appear in hospital_info.md; otherwise block and send "I don't have    │
     │   that information; our staff can help." Tests: Rs 700 blocked, Rs 500  │
     │   allowed, 10am to 1pm allowed, 9am to 9pm blocked.                     │
     │ - Medical-advice safety net (after-model hook, small blocklist:         │
     │   dosages, drug names, "you have", "it's probably", "nothing to         │
     │   worry"): replaces the reply with a standard "I can't give medical     │
     │   advice, but I can book you a doctor." Booking and billing prompts     │
     │   also forbid advice.                                                   │
     │ - [LIMIT] Cannot be guaranteed by code: non-numeric unsupported claims  │
     │   ("we accept Star Health", scenario 09 style), advice phrased outside  │
     │   the blocklist, advice in Hinglish. Those rely on prompts and are      │
     │   measured by evals (scenario 09 plus my own variants); DESIGN.md says  │
     │   so.                                                                   │
     │ - No retrieval infrastructure: the file is about 50 lines.              │
     │                                                                         │

     │ 3. Critical design decisions                                            │
     │                                                                         │
     │ 3.1 Confirmation and pending actions [REQ read-back + clear yes;        │
     │ mechanics REC]                                                          │
     │                                                                         │
     │ Plain language: when the model wants to write, code parks the call and  │
     │ builds the read-back from the parked args (doctor, day, date, time, or  │
     │ bill and amount). The model writes friendly prose in the patient's      │
     │ language; code appends the details block so the patient confirms        │
     │ exactly what will run. Pending = {id (random), tool, args, args_hash,   │
     │ details_text, agent, phone, created_turn}.                              │
     │                                                                         │
     │ Authorization rule (all must hold): (1) a pending action exists for     │
     │ this phone+session and was created in the previous turn; (2) the Haiku  │
     │ judge, shown the stored read-back and the patient's message, returns    │
     │ confirm; (3) a code check agrees: message is short (about 20 words or   │
     │ fewer), contains an affirmative token from a small EN/HI/Hinglish list  │
     │ (yes, ok, okay, sure, confirm, go ahead, haan, ji, theek hai, kar do,   │
     │ book it, हाँ, ठीक है ...) and no blocker token (no, not, don't, but,      │
     │ instead, wait, change, nahi, mat, lekin ...). Any disagreement means    │
     │ not confirmed (fail closed; patient is re-asked). "Okay book whatever"  │
     │ passes (specific read-back plus affirmative).                           │
     │                                                                         │
     │ ┌───────────────────────────┬────────────────────────────────────┐      │
     │ │       Patient reply       │               Result               │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │                           │ consume pending before executing   │      │
     │ │ clear yes                 │ (so a retry/double "yes" can't run │      │
     │ │                           │  twice); execute stored call       │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ yes but qualified ("yes   │ not confirmed; treated as a        │      │
     │ │ but 6pm", "yes and also   │ change; old pending cleared; agent │      │
     │ │ cancel...")               │  proposes new read-back            │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │                           │ old cleared; agent re-proposes;    │      │
     │ │ changed details           │ new pending replaces (max one      │      │
     │ │                           │ pending)                           │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ question                  │ cleared (fail closed); answer,     │      │
     │ │                           │ then agent re-offers a read-back   │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ rejection                 │ cleared; no write                  │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ topic change              │ cleared; router picks the agent    │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ asks for a person         │ cleared; handoff, handoff=true     │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │                           │ cleared before anything else; no   │      │
     │ │ emergency                 │ execution even if the message says │      │
     │ │                           │  "yes"                             │      │
     │ ├───────────────────────────┼────────────────────────────────────┤      │
     │ │ unclear/maybe             │ cleared; clarifying question       │      │
     │ └───────────────────────────┴────────────────────────────────────┘      │
     │                                                                         │
     │ Retention rule: a pending action lives across exactly one patient       │
     │ message boundary; every outcome clears it. [LIMIT] A patient who asks a │
     │ side question must re-confirm; accepted for safety and simplicity.      │
     │                                                                         │
     │ 3.2 Safety at execution time [REQ own-data, 4-hour rule; mechanics REC] │
     │                                                                         │
     │ The confirmed action is run by agentcore.execute_tool_call(registry,    │
     │ name, args, ctx), the same function run_agent uses for model-requested  │
     │ calls: Pydantic validation, before-tool hooks, execution, after-tool    │
     │ hooks, trace span, error-to-result. ctx.approved (fingerprints of       │
     │ confirmed calls) is set only by app code from the patient's own         │
     │ message, never by model or tool output. Hook order for every write:     │
     │ ownership (fresh list for ctx.phone; not found returns the same generic │
     │ "not found" as a missing id) -> state (appointment exists and is        │
     │ booked; bill unpaid; slot in the future per hospital /now) -> 4-hour    │
     │ (fresh /now; strictly less than 4h blocks, exactly 4h allowed; sets     │
     │ handoff) -> confirm gate (allow only if fingerprint is approved,        │
     │ otherwise park). Anything that changed since read-back blocks the write │
     │ and the model explains.                                                 │
     │                                                                         │
     │ 3.3 Write recovery [REQ never claim, never double-book; strategies REC, │
     │ from mock API]                                                          │
     │                                                                         │
     │ Outcomes: success (2xx, or verified state), definite failure (409       │
     │ slot_taken, 400/404 with code, or verified not-applied), unknown        │
     │ (timeout, connection reset after send, 503 on a write, malformed body). │
     │                                                                         │
     │ Write: Reads                                                            │
     │ Strategy: Retry with backoff (up to 3).                                 │
     │ ────────────────────────────────────────                                │
     │ Write: Book                                                             │
     │ Strategy: idempotency_key = per-operation id (the pending action's      │
     │   random id): stable across retries of that one operation, new for      │
     │   every new operation (a content hash would wrongly return an old       │
     │   cancelled booking for a re-booking). On unknown: retry same key       │
     │   (up to 2 more); still unknown: list the phone's appointments and      │
     │   match doctor+start; found = success, list ok and no match = not       │
     │   booked, list fails = unknown. slot_taken = definite failure           │
     │   (offer other slots, new read-back needed).                            │
     │ ────────────────────────────────────────                                │
     │ Write: Reschedule                                                       │
     │ Strategy: No key, so never blind-retry. On unknown: fetch the           │
     │   appointment fresh. start == new_start = success; start ==             │
     │   old_start = not applied, retry once (may now be slot_taken =          │
     │   definite failure); unclear = unknown.                                 │
     │ ────────────────────────────────────────                                │
     │ Write: Cancel                                                           │
     │ Strategy: Same as reschedule: verify status. cancelled = success;       │
     │   booked = retry once; not_active is verified, not trusted.             │
     │ ────────────────────────────────────────                                │
     │ Write: Payment link                                                     │
     │ Strategy: No automatic retry after an unknown outcome (cannot           │
     │   verify, duplicates possible). Retry only when the request             │
     │   provably never left (connection refused before send). Unknown:        │
     │   tell the patient honestly, offer "try again (may create a second      │
     │   link)" as a new confirmed action with a new id, or handoff.           │
     │                                                                         │
     │ Tools return structured {outcome: success|failed|unknown, ...}; code    │
     │ appends an authoritative outcome block ("Booked: Dr. X, Fri 4 Dec       │
     │ 17:30, ref A1007" / "Not confirmed; staff will check"). Unknown also    │
     │ flags handoff. [LIMIT] The model's free-text prose could still          │
     │ contradict the block in some language; mitigated by the truth           │
     │ instruction in tool results, the block, and evals. Cost note [ASSUME]:  │
     │ the no-retry payment-link rule may fail scenario 10 in about the share  │
     │ of chaos runs where that call 503s; reported honestly.                  │
     │                                                                         │
     │ 3.4 Emergency handling [REQ before router, EN/HI/Hinglish; mechanics    │
     │ REC]                                                                    │
     │                                                                         │
     │ Order on every message: (a) normalized keyword/phrase layer (English,   │
     │ Devanagari Hindi, Hinglish) -> immediate emergency, no model call; (b)  │
     │ Haiku JSON classifier via call_model (short timeout, 1 retry, strict    │
     │ Pydantic parse). Classifier failure (timeout, API error, invalid JSON): │
     │ fail safe. If a soft symptom word is present (pain, dard, seene,        │
     │ saans, khoon, bleeding, behosh, chakkar, ...), treat as emergency;      │
     │ otherwise continue read-only for this turn (confirm gate refuses        │
     │ writes) with a "if this is an emergency call 108" line. Emergency reply │
     │ is a fixed bilingual template (English plus Hindi): 108 or nearest ER   │
     │ (ours is open 24h), no medical advice. Flags: emergency=true,           │
     │ handoff=true (staff flag; there is no real paging system in scope),     │
     │ agent=safety. Pending is cleared.                                       │
     │                                                                         │
     │ Tests (offline, no key): table of EN / Devanagari / Hinglish phrases    │
     │ including scenario 08's text; classifier                                │
     │ true/false/invalid-JSON/exception/timeout via FakeClaude; emergency     │
     │ while a confirmation is pending (message says "yes", nothing written,   │
     │ pending cleared). [LIMIT] Recall is only measured on tested phrases;    │
     │ Marathi and indirect phrasing ("he isn't responding") rely on the       │
     │ classifier; false alarms are accepted, misses are not; we never claim   │
     │ 100%.                                                                   │
     │                                                                         │
     │ 3.5 Identity and trace isolation [REQ own-data; mechanics REC]          │
     │                                                                         │
     │ - Verified phone enters only through RunContext built in /chat. No tool │
     │   input schema contains a phone or patient identity; registry           │
     │   validates with unknown fields forbidden, so a model-supplied phone is │
     │   rejected. book forces phone = ctx.phone; patient_name is              │
     │   length/charset limited.                                               │
     │ - Ids are validated by pattern (^A\d+$, ^B\d+$, ^d\d+$), dates and      │
     │   times parsed, path segments URL-quoted, and the hospital client       │
     │   exposes only named functions (no _admin). A test greps agent_service/ │
     │   for _admin.                                                           │
     │ - Sessions: SessionStore.bind(session_id, phone) is first-use-wins; a   │
     │   different phone reusing a session id gets 409 and no data. State      │
     │   therefore maps 1:1 session_id -> phone, and GET /trace/{session_id}   │
     │   can never mix two patients (no collision handling needed).            │
     │ - [LIMIT] /trace/{session_id} is unauthenticated per the spec; anyone   │
     │   with the id can read it. Mitigation without auth infrastructure:      │
     │   phone masked (******3210), no API keys or headers ever stored, error  │
     │   text truncated. DESIGN.md lists trace auth as a production gap.       │
     │                                                                         │
     │ 3.6 Consistent runtime hooks [REQ hooks around model and tool calls]    │
     │                                                                         │
     │ Router, emergency classifier, confirmation judge, human-agent reply and │
     │ specialists all call call_model, so all get timeout, retry/backoff,     │
     │ before/after-model hooks and a trace span (cost per conversation = sum  │
     │ of spans for one trace_id). Real use of model hooks: a per-turn         │
     │ cost/call budget guard. agentcore only knows Allow | Block(reason) |    │
     │ Confirm(details); "Confirm" means "this call needs end-user consent".   │
     │ It never knows what a booking is. The hospital hook decides which tools │
     │ are writes and what details to show, and checks ctx.approved.           │
     │                                                                         │
     │ Parallel tool calls: executed in order; every tool_use gets a           │
     │ tool_result. After the first Confirm, the loop skips all remaining      │
     │ calls in that response with is_error results ("not executed: another    │
     │ action is awaiting confirmation") and ends the turn after the model's   │
     │ next reply. A Block does not skip the others. Two writes proposed at    │
     │ once means only the first is parked.                                    │
     │                                                                         │
     │ 3.7 Context and handoffs [REQ context carries across handoffs]          │
     │                                                                         │
     │ One shared text history per session; every agent sees the whole         │
     │ conversation, so no re-asking. Tool traffic stays inside a turn. This   │
     │ is sufficient because the code-appended details/outcome blocks (ids,    │
     │ doctor, date, time, bill, amount) are part of the stored assistant      │
     │ text, and agents can re-fetch live data with read tools. Structured,    │
     │ not in prose: pending (bound to phone and session, never trusted from   │
     │ text), active_agent. History capped at 30 messages. [LIMIT] An old fact │
     │ beyond the cap is forgotten; typical chats are far shorter.             │
     │                                                                         │
     │ 3.8 Information safety [REQ facts only from hospital_info.md, no        │
     │ medical advice]                                                         │
     │                                                                         │
     │ - Info agent has no tools and receives the whole hospital_info.md in a  │
     │   delimited block; rules: answer only from it, otherwise say you don't  │
     │   know and offer staff.                                                 │
     │ - Number-grounding guard (after-model hook, deterministic): every       │
     │   currency amount, clock time and phone number in an info reply must    │
     │   appear in hospital_info.md; otherwise block and send "I don't have    │
     │   that information; our staff can help." Tests: Rs 700 blocked, Rs 500  │
     │   allowed, 10am to 1pm allowed, 9am to 9pm blocked.                     │
     │ - Medical-advice safety net (after-model hook, small blocklist:         │
     │   dosages, drug names, "you have", "it's probably", "nothing to         │
     │   worry"): replaces the reply with a standard "I can't give medical     │
     │   advice, but I can book you a doctor." Booking and billing prompts     │
     │   also forbid advice.                                                   │
     │ - [LIMIT] Cannot be guaranteed by code: non-numeric unsupported claims  │
     │   ("we accept Star Health", scenario 09 style), advice phrased outside  │
     │   the blocklist, advice in Hinglish. Those rely on prompts and are      │
     │   measured by evals (scenario 09 plus my own variants); DESIGN.md says  │
     │   so.                                                                   │
     │ - No retrieval infrastructure: the file is about 50 lines.              │
     │                                                                         │

  Timeouts and retries (agentcore/model.py)
  - Timeouts: each attempt gets its own timeout, capped by what is left of an
    overall budget. The defaults are 30 s per attempt and 90 s overall.
  - What gets retried: HTTP 408, 409, 429 and 5xx (including 529 "overloaded"),
    plus connection errors and timeouts. Other client errors (400, 401, 404 and
    so on) fail immediately.
  - Backoff: it doubles each time (1, 2, 4 s) up to a 20 s cap, with optional
    jitter. A Retry-After header is honoured, up to the same cap. A retry that
    wouldn't fit in the budget is skipped.
  - SDK retries: each call uses client.with_options(max_retries=0), so the SDK's
    own 2 retries can't multiply ours. I checked this on the real client: the
    default is 2 and the override gives 0. No network was used for that.
  - Failures in the loop: run_agent now returns api_error when retries run out
    and timeout when the budget is gone. The new max_seconds argument bounds the
    whole run.
  - Failed attempts in the trace: every attempt leaves a span, including failed
    ones. Each span records the attempt number and an error like "RateLimitError
    429", never the SDK's error text. The exception we raise also hides that
    text.
